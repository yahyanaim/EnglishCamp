# Advanced administration

Routes: `/admin/login`, `/admin/dashboard`, `/admin/learners`, `/admin/invitations`, `/admin/analytics`, `/admin/achievements`, `/admin/infrastructure`, `/admin/settings`.

The existing hashed management key, secure HttpOnly/SameSite cookie, eight-hour D1 sessions, same-origin checks and logout remain authoritative. Worker authorization covers administrative HTML and exported RSC payloads, including encoded paths. A learner session grants no administrative access. Management mutations have an additional session-scoped rate limit. The learner entrance no longer advertises administration. No secrets or billing settings are changed.

Migration 0007 adds only `cloud_admin_summaries` and two date indexes. It changes no learner/progress/note records. Cached summaries contain recorded totals, canonical course credits, actual signature-matched stages, badge IDs/timestamps and quiz score summaries. They contain no notes, microphone recordings, private answers, recovery credentials or session hashes. Profile deletion cascades to its summary. The cache retains data only while its learner exists.

Each data request refreshes at most five changed profiles, identified by the existing progress revision; it never rescans all raw progress JSON. A visible pending counter tells the owner to refresh further batches. Learning charts cover a bounded maximum of 201 summarized profiles (appropriate for the initial 100–200 learners), and disclose partial coverage. Account counts and XP totals query all registered online accounts. There is no continuous polling, paid telemetry, extra database or background service.

Date filters apply only to timestamped registrations, redemptions, event-ledger activity, quiz attempts and badge awards. Historical imported activity may be incomplete. Device-only guests and unsynced work are unknown. Legacy lesson/course credits are distinguished from recorded guided, independent and assessment-stage evidence. Neither XP, self-reviewed speaking/writing nor course completion is an official proficiency assessment. Learner detail shows server revision/update, not an invented live synchronization status.

Directory and invitation APIs use bounded 25-row pagination and validated filters. Directory sorting applies to the full result set, with stable tie-breaking, ID/name search, independent access/activity filters and clamped pages. Learner filtering supports status, recent recorded activity, name and registration period. Details expose only authorized account and learning summaries. Suspension requires confirmation; it preserves all learning records. Existing creation limits, single-use invitations, expiry, revocation and admissions controls remain. Full invitation codes are displayed only at creation.

`scripts/admin-coverage.cjs` generates read-only catalogue metadata from the actual course data, current `MOCK_PAPERS`, achievement definitions and published media. The existing Cloudflare build refreshes these manifests. Course editing remains a repository workflow; no conflicting D1 editor is introduced.

Infrastructure checks execute a lightweight D1 read and show sanitized configuration flags. Provider configuration is explicitly not claimed to be a live availability check. The billing feed displays its unavailable state; uncollected API/sync error charts are omitted. The GitHub commit is displayed when supplied by the deployment build. Shared request counters come from the existing quota buckets; they are not provider billing or successful-assessment counts. Authentication counters count requests, not confirmed failures. Observability stays disabled, OpenAI assessment stays disabled, Cloudflare remains Free and the Modal $1 cap remains unchanged.

The only lint configuration change scopes an existing Next.js lint rule to the established local `module` variable in `courseProgress.ts`; its code and completion behavior remain unchanged. Existing hook/image warnings are not hidden globally.

Future work, requiring separate scope: instructor roles/classes, centrally authorized assessment workflows, a deliberate versioned content editor, provider billing integrations and opt-in operational error aggregation. None is presented as an existing feature.

The Worker preservation hash is updated only for the reviewed no-store protection on admin assets, including when invitation gating is disabled. Dedicated routing/cache authorization tests cover that change; teaching banks, fonts and learner stores retain their existing preservation checks.

## Dashboard visual reference

The administration presentation follows the floating workspace in [AI-hub's AdminDashboardClient](https://github.com/yahyanaim/AI-hub/blob/main/components/admin/AdminDashboardClient.tsx): grouped pill navigation, a compact desktop icon rail, theme utilities and a learner detail drawer. The owner's WebPulse screenshot supplies the overview composition: one five-statistic strip, a wide two-series activity chart, an XP area chart, an open access gauge, then course progress and recent learners. EnglishCamp retains its palette, fonts, faceted SVG artwork, learning content, APIs, permissions and service limits. No reference-specific orange palette, traffic/geography metrics or previous-period percentages are invented.

Time charts use only timestamped records returned by EnglishCamp. Thin curves interpolate between recorded points; gaps are not filled with invented observations. A single observation stays a point or bar. Values remain available in expandable tables, and points can be focused by keyboard or tapped to show their actual values. Metric coverage explanations remain available under “How metrics work.” SVG utilities use the same artwork palette as the existing learning icons; no chart dependency or polling is added.

## Essential analytics and independent admin entrance

The overview shows five essentials: registered learners, recorded XP, completed lessons, quiz attempts and earned badges. Analytics is limited to registrations, learning events, quiz score distribution and course credits. Achievements shows category and badge counts. The data API remains unchanged; the presentation omits redundant charts and the former full-report accordion. At tablet widths the icon rail becomes a labelled drawer; phone layouts stack the chart panels and use a two-column statistic strip. Authentication retains the existing independent login pattern.

`/admin/login` is an independent administrator entrance. It calls only the existing admin session/login endpoints, uses the existing private administrator key and receives the separate administrator cookie. Learner invitation/recovery sessions do not grant admin permissions, and signing an administrator out does not sign learners out. The learner invitation flow remains `/invite`. The invitation management page redirects expired administrators to the dedicated admin login; it no longer includes a second inline sign-in form. No extra administrator password database or pretend email field is introduced.

Admin routes render outside the learner session/progress/notes providers. This keeps learner synchronization and local profile restoration out of the admin entrance, while retaining the existing independent server-side cookies and permissions. The preservation contract changes only for this reviewed layout boundary; learner stores and teaching banks are unchanged.

## Management screens and invitation recovery

The owner removed the Courses screen; course data, catalogue API and progress analytics remain intact. The seven navigation entries use distinct faceted artwork rather than the document/plan/review variants. Registered accounts follows the actual AIhubtools table: rounded table shell, account avatars, copyable public profile IDs, search, filter pills, sortable headers, status tags and numbered pagination. CSV exports contain the visible page only and neutralize spreadsheet formula prefixes in learner names.

Invitations has one paginated endpoint. It no longer fetches learners or learning reports and does not trigger summary backfill. Changes to search/filters abort stale reads. Creating a batch has an immediate client submission lock; the server checks ready-code capacity and inserts the full batch with one conditional SQLite statement. Over-capacity batches insert nothing. Full codes exist only in the creation response and temporary browser state; the save dialog offers copy/download and warns before discarding unsaved codes. No code is added to local storage or analytics. Revocation is atomic, reports codes used or expired since the list loaded, and is idempotent for an already-revoked code.

Settings contains confirmed admissions control, the existing read-only practice limits, local appearance preferences and administrator sign-out. Infrastructure uses service cards, a service table, existing shared counters and the current deployment version. Provider configuration is labelled separately from live Worker/D1 checks. There are no fabricated provider health, spending or deployment-history feeds. There is no new database migration, provider request, paid binding or change to the Modal cap.

SQL implementation references: [Cloudflare D1 result metadata](https://developers.cloudflare.com/d1/worker-api/return-object/), [D1 bound JSON queries](https://developers.cloudflare.com/d1/sql-api/query-json/), [SQLite write isolation](https://www.sqlite.org/isolation.html).
